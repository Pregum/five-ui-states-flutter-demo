# 予備調査で分かったこと（2026-09-26）

モデル `gpt-6-luna`（`reasoning.effort: none`）、プロンプト「1 から 1200 まで 1 行ずつ数字を書いて」。
本番の実験（`bin/cancel_billing.dart`）はまだ実行していない。以下は `bin/probe.dart` などでの予備観察。

## 1. ストリームの届き方

- 最初の約 3 秒（約 150 行）は、1 トークンずつ（`"1"`, `"\n"`, `"2"` …）流れてくる
- そのあと約 10 秒は何も届かない
- 残りの約 1000 行は、最後に数個の大きな差分としてまとめて届く（完了は約 13 秒後）
- 300 行ではこの現象は起きず、約 3.7 秒で最後まで少しずつ届いた

→ 行数で中断タイミングを決めると「300 行目を受け取った時点で全部届いていた」ことになるため、本番では「最初の差分から何秒後」で中断する。
→ スライドの材料：ユーザーから見ると、途中で固まったように見える時間がある。

## 2. 途中で中断した応答は保存されない

- 最初の差分の直後に `subscription.cancel()` すると、`store: true` でも `GET /v1/responses/{id}` は 45 秒後まで 404
- 最後まで受け取った応答は `status: completed` で取り直せる

→ 「どこまで生成・課金されたか」はアプリ側から確かめられない。課金は利用量 API（管理者キー、1 分単位）で見る必要がある。

## 3. 利用量 API での見え方（暫定）

| 時刻 | 何をしたか | 利用量 API の記録 |
|---|---|---|
| 16:32 | 最後まで受信 | 1 リクエスト / 出力 2610 |
| 16:33 | 最初の差分で cancel | **記録なし** |
| 16:34 | 最初の差分で cancel + close | **記録なし** |
| 16:35 | 300 行で cancel（実際は全部受信済み） | 1 リクエスト / 出力 2610 |
| 16:37 | 300 行を最後まで受信 | 1 リクエスト / 出力 603 |
| 16:38 | 1200 行を最後まで受信 | 1 リクエスト / 出力 2604 |
| 16:39 | 最初の差分で cancel | （確認時点で未反映） |

→ 早い段階で中断したリクエストは課金されていない可能性がある。反映の遅れの可能性もあるので、本番の実験で確かめる。
→ 利用量 API の入力トークンは、応答の `usage.input_tokens` より多く出ることがある（29 → 40 など）。

## 本番の実験の結果（2026-09-29）

`dart run bin/cancel_billing.dart --reps 3`（`gpt-6-luna`、`reasoning.effort: none`、6 条件 × 3 回）。
生データは `results/2026-09-29T16-00-11.json`（計測値のみ。キーや応答本文は含まない）。利用量 API は 16:12 と 16:19 に取り直し、同じ値だった。

| 条件 | 受信した量（3 回） | 課金リクエスト | 課金 output_tokens |
|---|---|---|---|
| 最後まで | 1199 行（2604 トークン） | 1 / 1 / 1 | 2604 / 2604 / 2604 |
| 最初の差分で中断 | 0 行 | 0 / 0 / 0 | 0 |
| 1 秒後に中断 | 55〜87 行（約 120〜190 トークン） | 0 / 0 / 0 | 0 |
| 2 秒後に中断 | 154〜157 行（約 335〜340 トークン） | 0 / 0 / 0 | 0 |
| 2 秒後に中断 + `client.close()` | 156〜158 行 | 0 / 0 / 0 | 0 |
| 6 秒後に中断（無音の時間帯） | 157〜158 行 | 0 / 0 / 0 | 0 |

- **途中で中断した 15 回は、どれも利用量 API に 1 件も記録されなかった**。受け取った分（最大で約 340 トークン）も課金されていない
- 反映の遅れではない：最後まで受信した回は、実験直後（16:03）は 3 回目だけ未反映だったが 16:12 には反映された。中断した回は実行から 13〜28 分たっても 0 のまま
- 別のモデル名で記録されていないことも確認した（モデルで絞らずに 15:40〜16:05 を集計しても、記録は最後まで受信した 3 件だけ）
- `cancel()` だけでも `client.close()` を足しても結果は同じ
- 1 秒後の受信量がばらつく（55〜87 行）のは、最初は 1 トークンずつ流れる速さが回ごとに違うため。2 秒後と 6 秒後がほぼ同じなのは、予備調査で見た「約 155 行のあと約 10 秒無音」を再現している

### どこまで言えるか

- 言えること：OpenAI の Responses API（このモデル・この条件）では、**応答が完了する前にストリームを切ると、それまで受け取った分も含めて利用量に計上されなかった**
- 言えないこと：
  - これは利用量 API での見え方。請求額（Costs API・請求書）で同じかは未確認。数日後に Costs API（1 日単位）でも確かめるとよい
  - OpenAI の仕様として保証されたふるまいではない。ほかのモデル・推論あり・ほかの社（Anthropic、Gemini）では変わりうる
  - 「サーバー側で生成が止まったか」は分からない。分かるのは「計上されなかった」ことだけ

→ スライドの「途中キャンセルでも、そこまでの生成分は課金される」は、少なくともこの実測とは合わない。一般論として断言せず、「サービスによって違う。実測したら OpenAI では計上されなかった」のように直す必要がある。

## 本番の実験の手順

```bash
cd experiments/cancel_billing
# .env に OPENAI_API_KEY と OPENAI_ADMIN_KEY（読み取り専用）を書く。.env は git に入らない
dart pub get
dart run bin/cancel_billing.dart --reps 3   # 6 条件 × 3 回、1 回ごとに 1 分枠を使うので約 20 分
dart run bin/usage.dart results/<日時>.json  # 反映が遅れたときに課金トークンだけ取り直す
```

条件：最後まで ／ 最初の差分で中断 ／ 1 秒後 ／ 2 秒後 ／ 2 秒後 + client.close() ／ 6 秒後（無音の時間帯）
